# Build Prompt: Kanz Bakery Web Application

Build a polished, mobile-first web application for a bakery called **Kanz Bakery**.

The application should serve as both:

1. A public-facing digital storefront where customers can learn about the bakery and browse its products.
2. A foundation for future online ordering, catering, customer accounts, loyalty features, promotions, and operational integrations.

The implementation should prioritize **clean architecture, maintainability, extensibility, security, accessibility, and excellent user experience** rather than building the fastest possible prototype.

---

## Product Goals

Create a modern bakery website that allows customers to:

* Learn about Kanz Bakery, its story, values, and specialties.
* Browse the bakery menu by category.
* Search and filter menu items.
* View detailed information about each item.
* See product images, descriptions, ingredients, prices, allergens, and availability.
* Rate products and optionally leave reviews.
* Submit inquiries for:

  * Bulk orders.
  * Corporate orders.
  * Events.
  * Catering.
* Select a preferred date and time for bulk or catering requests.
* Easily contact the bakery.
* Use the entire application comfortably from mobile, tablet, and desktop devices.

The initial version does **not** need to implement full online payment or real-time delivery logistics unless explicitly added later. However, the architecture should make these features easy to introduce in the future.

## 5. Ratings and Reviews

# Architecture Requirements

Use a clean, modular project structure.

Do not build the entire application as one large component, route file, or service.

Organize the application by clear domains or features, such as:

* Catalog.
* Products.
* Categories.
* Reviews.
* Catering.
* Content.
* Authentication.
* Administration.

Separate:

* UI components.
* Pages and routes.
* Business logic.
* Data access.
* Validation.
* API logic.
* Database models.
* Shared utilities.

Prefer reusable components and abstractions only where they provide clear value. Avoid unnecessary over-engineering.

Business rules should not be deeply embedded inside UI components.

Create clear boundaries between the frontend, application logic, and persistence layer.

Use consistent naming conventions and project organization.

---

# Data and Database Design

Use a proper relational database.

Create explicit models and migrations for the main entities.

At minimum, consider:

* Products.
* Categories.
* Product images.
* Reviews.
* Catering or bulk-order inquiries.

Use:

* Stable unique identifiers.
* Created and updated timestamps.
* Database constraints.
* Foreign keys.
* Appropriate indexes.
* Unique constraints where required.

Avoid storing important structured business information inside large unstructured JSON fields unless there is a clear reason.

Provide seed data so the application looks complete when first launched.

Use realistic bakery sample content rather than generic placeholder text such as "Lorem ipsum."

---

# API and Backend Principles

All important business operations must be validated server-side.

Use a consistent API structure.

API responses should have:

* Appropriate HTTP status codes.
* Predictable error responses.
* User-safe error messages.

Do not expose:

* Stack traces.
* Database errors.
* Secrets.
* Internal implementation details.

Avoid duplicating business rules across multiple endpoints.

Design endpoints so future mobile applications or external integrations could consume the same backend.

---

# Security Requirements

Apply secure defaults from the beginning.

At minimum:

* Never expose secrets or API keys in frontend code.
* Store secrets in environment variables.
* Do not commit secrets to the repository.
* Validate and sanitize all user input.
* Protect against SQL injection by using the framework's safe ORM or parameterized queries.
* Protect against cross-site scripting.
* Protect state-changing operations against CSRF where applicable.
* Apply secure authentication practices.
* Hash passwords using an established password-hashing mechanism.
* Implement authorization checks on protected resources.
* Avoid relying only on hidden frontend elements for access control.
* Restrict administrative routes.
* Validate uploaded files by type and size.
* Rate-limit abuse-prone endpoints where appropriate.
* Avoid exposing sensitive internal information through error messages.
* Use secure cookie settings when cookies are used.
* Follow least-privilege principles.

Do not create custom cryptography or custom authentication mechanisms when established framework capabilities are available.

* Large mobile devices.
* Tablets.

* Buttons and controls are touch-friendly.
* Forms are easy to complete on mobile.
